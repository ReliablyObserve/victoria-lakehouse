- **Follow-ups to the unreadable-object change (#503, #751): `query.max_live_bytes` now reserves an estimate of the decoded bytes in flight, a read that cannot read an object answers 502, two queries sharing a download no longer fail each other, and the gone-object tolerance is documented honestly.** (1) The ceiling counted decoded blocks only after they were decoded, which bounded nothing: each worker already holds a decoded block while the consumer is busy. Before it decodes a row group, a file worker now reserves an estimate of that row group's decoded size against the ceiling, taken from the footer it has already read (per projected column the larger of the uncompressed size and the value count times the longest min/max statistic or the text width of a number; never the compressed size; no request is added), and waits while the reserved bytes would pass it; one row group larger than the ceiling is read alone. The unit is the row group, so a 128 MiB object does not take the whole 512 MiB ceiling for itself. Measured: the decoded bytes in flight stay within the ceiling plus one block for compressible and incompressible data, cold and warm footer cache, filtered and unfiltered, in both binaries (62.6 KB against a 93.4 KB ceiling on a run that peaks at 249 KB with no ceiling), and a scaled model of the production read (objects at 1/64, ceiling of 4.5 objects, file budget of 2.5, 20 ms of S3 latency) runs the cold wildcard read in 649 ms against 653 ms before #503 and the warm phrase read in 150 ms against 172 ms, within noise. The documentation of `query.max_live_bytes` (flag, field, `docs/operations/sizing.md`) says what the ceiling is: an estimate, which under-counts a dictionary-encoded text column whose min and max statistics are short while its values are long (461x on a constructed row group; #807, known gap, pinned by a test), and which makes a ceiling that holds fewer than about four row groups (row groups estimated over about 128 MiB at the default) slow a query, the warm phrase read 155 ms against 87 ms in the scaled model, none from four row groups up (set `query.max_live_bytes` to four times a row group's decoded size for full speed). `lakehouse_query_memory_budget_exceeded_total` counts waits (name kept). (2) **A read that cannot read an object it selected answers 502 Bad Gateway** (`cannot read <key>: <cause>`), the status upstream gives a read whose storage node is unavailable, on every `/select/logsql/*` endpoint (stats included, which answered 422) of both binaries; the first version left upstream's default for an error with no status, 400, which clients that retry only 429/500/502/503/504 would not retry. The streamed `/select/logsql/query` answers 200 with the error in the body when rows were already flushed, as upstream does. Jaeger's trace-by-ID and services stay 400 until VictoriaTraces keeps the status of an error it formats (#773). The caller's cancellation or deadline is unchanged. (3) A source object deleted by a compaction while a query runs is still skipped silently, so a running query can answer without rows that are in the merged object (#772, known gap; the earlier text said those rows are in the compacted object, which the query does not read); registry row `lh.query.removed_source_mid_query` and a test pin it. (4) A stalled consumer of one query can still hold the file-budget and row-group-decoder slots other queries need, at any ceiling, as before #503 (#793, known gap; registry row `lh.query.stalled_consumer_starves_slots`, a test at the default ceiling pins it); the earlier claim that the reservation prevents it is withdrawn. The `max_rows` ceiling still ends a read differently in logs and traces (#774). (5) Two queries that read the same object share one download, and the one that joined it no longer fails with the first query's `context deadline exceeded` (a 502 for a read nothing was wrong with): a joining caller waits no longer than its own context and reads the object itself when the download it joined ended with the first caller's context error (`cache.Group.DoCtx`, used by the whole-object download and the smart cache).
