- **A trace ID of 65,536 bytes or more no longer makes the `_trace_idx` footer decode into wrong entries, so trace-by-ID can no longer silently lose a file's spans (traces module and the shared writer and compactor; #768).** The index wrote each trace ID length as a `uint16`, so a longer ID wrapped the length and the payload decoded successfully into other entries; one such ID that sorted before a normal trace made the file pre-filter drop the file for the normal trace (0 of 1 span returned in the end-to-end reproduction, no error). Now the writer (flush and compaction, both go through `internal/traceindex.Marshal`) leaves only the over-long IDs out of the index and still lists every other ID of the file, so the index stays valid and complete for every ID it can hold. The meaning of the index changes, not its bytes: it lists every non-empty ID of at most 65,535 bytes. The readers follow: for a queried ID longer than that, or the empty ID (spans without a trace_id are stored but were never listed; `trace_id:=""` used to drop a file that held them), the file pre-filter keeps the file (including `trace_id:in(...)` when any listed ID is that long) and the footer lookup reports a miss, so the span scan decides; for a shorter ID, absence from the index still proves absence from the file. Each left-out ID is counted in the new `lakehouse_writer_trace_idx_omitted_total{reason="id_over_limit"}` (again whenever a compaction rewrites the same data) and logged; `lakehouse_writer_trace_idx_entries_total` counts the entries listed. A file with more than 2^20 IDs to list (the decoder already refused such an index; the writer had no cap) is written without an index (`reason="entries_over_cap"`), because a prefix of the IDs would break the rule above. VictoriaTraces puts no cap on a trace ID, so ingest does not reject one. The decoder now requires the value to be consumed exactly, so a file written by an older release with a wrapped length is read as having no usable index (kept, scanned) instead of yielding wrong entries. Valid indexes are unchanged byte for byte: the new decoder and the old one give identical results (zero divergences) on 300 random and extreme outputs of the new and of the historical writer, whose encoder is byte-identical in every earlier release (checked in git history: no padding, checksum or trailer); `Marshal` and `Unmarshal` of valid input are within noise of before (benchstat n=10 and n=20, all p>0.07; allocations identical). The logs binary does not write the index: the root module's trace writer has no caller outside tests, and the compactor writes it only in traces mode (`internal/compaction/compactor.go`, `case config.ModeTraces`); both modules still share the one codec. See [Open Parquet format](docs/open-parquet-format.md).
